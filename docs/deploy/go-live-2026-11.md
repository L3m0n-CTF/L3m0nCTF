### 0.2 Will 4 CPUs and 8 GB do?

- **Memory: yes, with room.** Measured on 14 November with the real images: the whole stack (CTFd, MariaDB, Redis, nginx, the anti-abuse overlay, all of monitoring, the mail relay, the host collectors) uses **866 MiB** when idle. Under load CTFd, the database and Prometheus grow; the sum of every container's ceiling is about 6.7 GB, and the real use will be far lower. What is **not** possible on this machine is running challenge containers next to it: that is why the instancer needs its own challenge host (Part 9.3).
- **CPUs: right for deployment, registration and testing; tight for the round.** The load measurement of October says CTFd alone needs about **2.8 cores for 300 players at the same time** (37 ms of CPU per request, 0.25 requests a second per player); the database, Redis, nginx and monitoring need about a sixth more. So 4 vCPUs carries roughly **250 to 300 players online at once**. If the round expects more, the machine can be resized in minutes (Part 9.2) but that needs the superior's agreement on the size. The k6 load test (Part 9.1) gives the real number on this machine.

## 2. The domain and Cloudflare [OWNER]

Today `l3m0nctf.xyz` answers from the registrar's parking name servers (`parking1.gen.xyz`, `parking2.gen.xyz`), so `play` and `crew` point at a parking address. ### 2.2 Add the site

1. Dashboard, **Add a domain**, enter `l3m0nctf.xyz`, plan **Free**.
2. Cloudflare reads the existing records. **Delete every record it imported** (they point at the parking address). Leave the zone empty.
3. Cloudflare shows **two name servers** (names ending in `.ns.cloudflare.com`). Copy both.

### 2.3 Point the registrar at Cloudflare

1. Log in to the registrar (**gen.xyz**) with the account that now owns the domain.
2. Open the domain `l3m0nctf.xyz`, then its **name servers** setting, choose **custom name servers**, and enter the two Cloudflare names. Save. (DNSSEC is not enabled for this domain, so nothing else needs switching off.)
3. Back in Cloudflare press **Check nameservers**. It can take a few minutes to a few hours (on 14 November: roughly 30 minutes after the change at the registrar). **Active** is not the end: Cloudflare then issues its own public certificate for the names (Universal SSL), and until it is ready every HTTPS request to `play` ends with a TLS "handshake failure" (alert 40) and `curl` exits with 35 or 7. On 14 November that took a further 10 to 20 minutes or so (the first working answer was seen within about an hour of the registrar change). Watch for the real answer with `openssl s_client -connect CLOUDFLARE_ADDRESS:443 -servername play.l3m0nctf.xyz`, which prints a certificate once it is ready.

**Check** (any computer): `nslookup -type=NS l3m0nctf.xyz 1.1.1.1` lists the two `.ns.cloudflare.com` names.

### 2.4 The origin certificate (secures the hop from Cloudflare to the VM)

The lead made the key on its side and kept it there; **you only paste the public request**, so no private key ever appears in a web page.

1. Zone `l3m0nctf.xyz`, **SSL/TLS**, **Origin Server**, **Create Certificate**.
2. Choose **Use my private key and CSR**. Paste the whole text of `1-origin-request.csr` (from `-----BEGIN CERTIFICATE REQUEST-----` to `-----END CERTIFICATE REQUEST-----`).
3. Hostnames: **leave Cloudflare's pre-filled names** (`l3m0nctf.xyz` and `*.l3m0nctf.xyz`); the wildcard covers `play` and `crew`, and nginx and the deploy check accept it. Validity 15 years. **Create**. (On 14 November typing the hostnames by hand, while the site was still *pending*, failed with "this zone is either not part of your account, or you do not have access to it", and a revoke attempt said "User is not authorized". Both were the pending state: do this step after the site shows **Active**.)
4. Copy the **Origin Certificate** text that appears and save it as `origin.pem` in the same Desktop folder. Nothing else on that page is needed.

### 2.5 The client certificate (proves a request came through *our* Cloudflare site)

1. **SSL/TLS**, **Origin Server**, section **Authenticated Origin Pulls**, zone-level, **Upload certificate**.
2. Paste the text of `2-aop-client-certificate.crt` and of `2-aop-client-PRIVATE-KEY-delete-after-upload.key`. Save, then **switch the zone-level toggle ON**.
3. **Delete the `.key` file from the Desktop folder** (it is the only copy outside Cloudflare, and the lead does not need it).

### 2.6 Strict mode and the rest

1. **SSL/TLS**, **Overview**: mode **Full (strict)**. **Edge Certificates**: **Always Use HTTPS** on, **Minimum TLS Version** 1.2, leave Cloudflare's own HSTS off (nginx adds it).
2. **Caching**, **Cache Rules**, two rules: (1) if the path does **not** start with `/themes/`: **Bypass cache**; (2) if it starts with `/themes/`: **Eligible for cache**, use the origin's cache-control.
3. **Security**, **Security rules**: rule one blocks `http.host eq "play.l3m0nctf.xyz" and starts_with(http.request.uri.path, "/admin")` (the crew uses the `crew` host). One **rate-limit rule**: `POST` to `/login` or `/register` on `play.l3m0nctf.xyz`, block after about 20 a minute from one address (a campus behind one address must not block itself, so do not go stricter). Leave **Bot Fight Mode** off until the rehearsal.
4. **Zero Trust**, **Access**, **Applications**, **Self-hosted**: host `crew.l3m0nctf.xyz`, no path, session 8 hours, policy **Allow** for the crew's e-mail addresses only, login method **One-time PIN**.

### 3.3 The VM: exactly 4 vCPUs and 8 GB

```bash
gcloud compute instances create l3mon-app \
  --zone=$ZONE --machine-type=e2-custom-4-8192 \
  --image-family=debian-12 --image-project=debian-cloud \
  --boot-disk-size=100GB --boot-disk-type=pd-balanced \
  --network=l3mon-net --subnet=l3mon-asia-south1 --address=l3mon-app-ip \
  --tags=l3mon-app,l3mon-web \
  --no-service-account --no-scopes \
  --metadata=enable-oslogin=TRUE,block-project-ssh-keys=TRUE \
  --shielded-secure-boot --shielded-vtpm --shielded-integrity-monitoring \
  --deletion-protection
```

`--no-service-account` gives the machine no Google identity at all (the account does not have the right to create one, and the platform needs none); OS Login ties SSH to a Google account; `block-project-ssh-keys` stops stray keys; Shielded VM protects the boot; `--deletion-protection` makes an accidental delete fail.

**Check:** `gcloud compute instances describe l3mon-app --zone=$ZONE --format="value(machineType.basename(),status)"` prints `e2-custom-4-8192  RUNNING`. If an organisation policy refuses something (for example an external address), the error names the policy: send it to the superior.

### 5.5 Who may open /admin, and the settings file

**How the crew reaches the administrator surface (changed on 14 November, tag `release-2026-11-14b`).** A list of addresses was refused by the project's superior, and the list was never only a list for `/admin`: nginx uses it for the administrator **API**, for **file uploads** and for the **maintenance-mode bypass** too (`deploy/nginx/nginx.conf`, `$admin_net`). Allowing every address would have switched all of that off for the whole internet. So the rule is now: the administrator surface is reachable from an address on the list **or on the crew host name** (`crew.<domain>`, the second name nginx serves). The platform host name never gets it. On the crew host three locks stack: Cloudflare Access (a one-time code sent to the crew's e-mail addresses), the platform's own administrator login (a user name and a password), and CTFd's checks behind that. **Cloudflare Access on the crew host is therefore not optional**: without it the crew host is protected by the password alone. The list of addresses stays (the deploy check needs at least one, and a script on the VM or a load test may use it); it is no longer the only way in.

```bash
sudo tee /etc/l3mon/admin-nets.conf > /dev/null <<'EOF'
# the addresses the crew opens /admin from (explicit addresses only, one per line, each ending in " 1;")
ADDRESS_OF_THE_OWNER 1;
EOF
sudo tee /etc/l3mon/production.env > /dev/null <<'EOF'
L3MON_ENV=production
L3MON_IMAGE_TAG=release-2026-11-14
TLS_DIR=/etc/l3mon/tls
ADMIN_NETS_FILE=/etc/l3mon/admin-nets.conf
EXTRA_HOST=crew.l3m0nctf.xyz
EOF
sudo chmod 644 /etc/l3mon/production.env
```

Replace `ADDRESS_OF_THE_OWNER` with the crew's real public IPv4 (`157.1.2.3 1;`) and IPv6 network (`2409:40f4:2014:466c::/64 1;`); never a private range. Part 6.4 shows how to add one in a minute. **A phone hotspot or a carrier network is a poor choice for this list:** on 14 November the same laptop was seen by nginx as three different IPv4 addresses within an hour (a carrier translating IPv6 to IPv4), so the `/admin` door kept refusing it. Use a stable network (campus, home) for the crew's admin work, or add each address as it appears.

If the crew host says 403 as well, the request did not arrive under that host name or nginx is older than `release-2026-11-14b`: `tools/compose.sh logs --tail 30 nginx | grep " /admin" | tail -3` shows what nginx saw. To let one address in without the crew host, add `ADDRESS 1;` to `/etc/l3mon/admin-nets.conf`, then `tools/compose.sh restart nginx`.

## 7. The extra pieces [LEAD, with the owner for the accounts]

Each is added to `L3MON_OVERLAYS` in `/etc/l3mon/production.env`, then `set -a; . /etc/l3mon/production.env; set +a; tools/compose.sh up -d --wait`. **Every new SSH session starts without these settings: source the file first.** If one misbehaves, take its name out and run the same command; the platform keeps working without it.

### 7.1 Anti-abuse: the overlay `identity`

Disposable e-mail addresses, look-alike team names, a limit on flag guesses per team, and the crew's evidence page at `/admin/l3mon/guard`. It needs no keys. Add `L3MON_OVERLAYS=identity` (and the campus networks later: `L3MON_GUARD_CAMPUS_NETS=a.b.c.d/n,...`).

### 7.2 Monitoring and the mail relay: the overlay `ops`

Add `L3MON_OVERLAYS=identity,ops` and, for the host collectors, `COMPOSE_PROFILES=host-metrics`. Then, once, create the database user the exporter reads with:

```bash
cd ~/L3m0nCTF && bash tools/ops/init_exporter_user.sh
```

Grafana is reachable only through a tunnel from the laptop: `gcloud compute ssh l3mon-app --zone=$ZONE --tunnel-through-iap -- -L 3000:localhost:3000`, then <http://localhost:3000> (user `admin`, password in `.secrets/GRAFANA_ADMIN_PASSWORD`). Alerts go to Discord when `.secrets/DISCORD_WEBHOOK_URL` holds a webhook address.

### 7.3 Mail: what lets a player finish registering [OWNER decides]

Every account is verified by e-mail, so **nobody can finish registering until mail works**. CTFd sends to the relay inside the platform, and the relay sends to a provider; a provider outage only delays mail. Choose one:

1. **The club's mailbox, quickest for the test phase.** If the club's Google Workspace mailbox allows an *app password* (2-Step Verification on, Account, Security, App passwords): `UPSTREAM_SMTP_HOST=smtp.gmail.com`, port `587`, user the mailbox, `MAILFROM_ADDR` the mailbox address (Google rewrites any other sender). A Workspace mailbox may send about 2,000 messages a day; the From line is the club's address, not `l3m0nctf.xyz`.
2. **Brevo or Amazon SES** (the right choice for the round: 250 teams of up to 4 can need about 1,000 verification mails on the first day; a free plan allows 300 a day, so buy the provider's paid month for that day). Their DNS records (SPF and DKIM) are added in Cloudflare with a **grey cloud**. SES needs its production-access request, which takes one to two days: ask now.
3. **No verification** (`verify_emails = false`): possible but not recommended (fake addresses, no password reset).

The lines go in `/etc/l3mon/production.env` (no secret among them), the provider's password in `.secrets/MAIL_PASSWORD` (the owner types or pastes it on the VM themselves):

```
UPSTREAM_SMTP_HOST=smtp.the-provider.example
UPSTREAM_SMTP_PORT=587
UPSTREAM_SMTP_USER=the-login-name
UPSTREAM_SMTP_TLS=true
MAILFROM_ADDR=the-sender-address
RATE_LIMIT_PER_MINUTE=30
RATE_LIMIT_PER_DAY=the-provider's-daily-limit
```

Then recreate the relay: `tools/compose.sh up -d --force-recreate --no-deps mail-relay`. Messages over the daily limit wait in the queue.

### 7.4 CAPTCHA (Turnstile)

The sign-in, registration and password-reset pages already draw the widget, and nginx sets no Content-Security-Policy yet, so the widget loads without any nginx change. With the keys from 2.8: put the **site key** in `/etc/l3mon/production.env` as `TURNSTILE_SITEKEY=...` and the **secret key** in `.secrets/TURNSTILE_SECRET` (then `chmod 644` like the other secret files), then recreate `ctfd`. Empty means off. **Check:** `/register` (open it briefly, 8.2) shows the widget and a form sent without the token is refused.

### 7.5 Backups (before any real registration)

The lead made an `age` key pair on the owner's laptop: the **public** half is on the VM, the **private** half is only in the owner's password manager. Nothing on the VM can read its own backups.

```bash
mkdir -p ~/L3m0nCTF/config/backup && echo "AGE_PUBLIC_KEY" > ~/L3m0nCTF/config/backup/recipients.txt
cd ~/L3m0nCTF && bash tools/ops/backup.sh --full --sink file://$HOME/backups/sink --recipients config/backup/recipients.txt
ls -l ~/backups/sink | head
```

There is no service account on this VM, so the off-host copy is a **pull from the laptop**: `gcloud compute scp --recurse l3mon-app:/home/USER/backups/sink ./backups-pulled --zone=$ZONE --tunnel-through-iap`. Pull at least daily (and before every change).

**Schedule it** (the monitoring reads the last-backup time from `deploy/ops/backup`, which Docker creates **root-owned** when the monitoring starts, so give it back to your user first, or the heartbeat cannot be written and the "backup stale" alert fires):

```bash
sudo chown "$USER":"$USER" ~/L3m0nCTF/deploy/ops/backup
crontab -e     # add the two lines below, with your real home folder
*/30 * * * * cd /home/USER/L3m0nCTF && set -a && . /etc/l3mon/production.env && set +a && bash tools/ops/backup.sh --full --sink file:///home/USER/backups/sink --recipients config/backup/recipients.txt --heartbeat /home/USER/L3m0nCTF/deploy/ops/backup/backup.prom >> /home/USER/backups/backup.log 2>&1
17 3 * * * find /home/USER/backups/sink -type f -mtime +7 -delete
```

A backup that was never restored is not a backup. **Restore test without touching the platform:** pull a backup to the laptop, check its checksum (the `.sha256` file holds only the hash), decrypt it with the private key (`age -d -i PRIVATE_KEY -o backup.tar FILE.tar.age`), unpack it (on Windows use `tar --force-local`, or `tar` reads `C:` as a host name), start a throw-away MariaDB, **create the database `ctfd` first** (the dump has no `USE` line) and load `db.sql.gz` into it. On 14 November this gave 37 tables including all eleven `l3mon_*` ones; the `users` table is empty until the first sign-in creates `organiser`. The full runbook for a real recovery is `docs/runbooks/03-database-recovery.md`.

### 7.6 Save everything needed to rebuild the machine

```bash
cd ~/L3m0nCTF && tools/export-state.sh --encrypt
```

It asks for a passphrase twice (not shown); for a run with nobody at the keyboard put the passphrase in a file and set `L3MON_STATE_PASSPHRASE_FILE` to it (shred the file afterwards). The result is one encrypted file under `backups/`; copy it to the laptop with `gcloud compute scp`, check its checksum, keep two copies, and keep the passphrase apart from the file in the password manager. It holds the database, uploads, every secret (including `FLAG_HMAC_SECRET`) and the certificates, so the whole platform can be rebuilt elsewhere with `docs/deploy/move-to-a-new-account.md`.

## 10. If something goes wrong

| What you see | Usual cause | What to do |
|---|---|---|
| `PERMISSION_DENIED ... compute.googleapis.com` | Part 1 not done | send Part 1 to the project administrator |
| Cloudflare **521** | VM off, nginx down, or the firewall rule does not list Cloudflare's ranges | `tools/compose.sh ps`; compare the rule with Cloudflare's list |
| Cloudflare **522 / 523** | wrong address in the `A` record or the firewall | compare with 3.2 |
| Cloudflare **525 / 526** | the origin certificate is missing, wrong, or misses `play`/`crew` | check `/etc/l3mon/tls` and 2.4; set Full (not strict) only while fixing |
| **400 No required SSL certificate was sent** for visitors | the client-certificate check is off, or the uploaded certificate is not from the authority on the VM | 2.5; check that `cloudflare-origin-pull-ca.pem` is the `rootca.crt` of the lead's folder |
| `/admin` shows 403 | the address is not in the list | 6.4 |
| `deploy check` says BLOCKED | see its own words | it names the file or setting |
| A container is `unhealthy` | a setting or a secret | `tools/compose.sh logs --tail 100 ctfd` (secrets are never logged) |
| Mail does not leave | wrong provider settings or password | `tools/compose.sh logs --tail 50 mail-relay`; the queue length is in Grafana |
| Everything is wrong after an update | a bad release | `docs/runbooks/10-rollback-deploy.md`: previous tag, same steps, never `down -v` |

If the whole project has to be left again, do not rebuild by hand: `docs/deploy/move-to-a-new-account.md`.
